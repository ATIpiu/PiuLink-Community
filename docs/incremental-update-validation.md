# 应用内增量更新验证（2026-11-27）

## 平台和入口

| 平台 | 首次安装带更新功能的预览 | 后续操作 |
| --- | --- | --- |
| Windows | 整合版 0.2.138，单端为 Host 0.2.136 或 Client 0.2.37 | 在程序窗口点击「检查更新」。检测到已安装整合版时，两端都选择整合版渠道。校验通过后可打开系统安装程序。 |
| Android | 正式签名的 nonRoot 0.3.225，通用 / ARM64 | 「设置 → 高级选项 → 检查更新」。直接读取当前安装的 APK 作为旧包，最后由系统确认安装。 |
| macOS / Linux 控制端 | 0.1.11 | 主窗口检查更新。找到新版本后可以手动选择原来的安装包，或使用自动找到的下载目录原包、更新缓存。完成后打开安装包所在目录。 |
| Linux 被控端 | 0.1.8 | `piulink-host update check`、`piulink-host update download [旧安装包路径]`。输出下载量和校验后的安装包路径。 |
| iOS | 0.1.3 未签名 IPA | 从「文件」选择旧的官方 IPA，或使用更新缓存。分享新 IPA 后仍需用自己的签名工具安装。 |

每个渠道独立比较数字版本。新发布的安装包通过 GitHub 资产的 SHA-256 校验后进入渠道。分块索引仅用于复用数据，最终生成的整个文件必须与该 GitHub 安装包的 SHA-256 一致。缺少可用旧包、旧包重压缩或服务器不支持 Range 时，下载量可能接近完整安装包。小版本首次进入这些渠道需要手动下载安装。

## Windows 和 DEB 的压缩布局

早期 Windows 整合版将会随项目更新的组件与运行库共同压缩，DEB 则把未压缩的安装内容作为一个持续的压缩流处理。小改动会影响大量压缩字节。0.2.138 的 Windows 整合版在不同 CAB 中存储应用和运行库，保留离线安装。0.1.11 客户端及 0.1.8 被控端的 DEB 改用按文件边界划分的标准 XZ 块。

本地 HTTP Range 对照使用两个版本的实际发布内容，分别以新布局重新打包。Windows 样本从 119.45 MiB 中下载 38.25 MiB，复用 68.0%。Linux x64 DEB 样本从 35.06 MiB 中下载 13.44 MiB，复用 61.7%。重建文件的 SHA-256 匹配，DEB 重新压缩前后完整 data.tar 的 SHA-256 也匹配。这组数字测试的是两端均采用新布局的情况。旧布局首次迁移可能仍需完整下载。

## 安装与回归

- 官网 Windows 默认下载为 0.2.136。开发机上实际执行了从 0.2.135 升级、破坏两个语言资源后的修复、完整卸载和重装。14 个已有配对和 53 项状态指纹均保留，平板使用原配对再次显示桌面。
- Windows 增量预览整合包使用两份公开的独立 MSI 对照，核对 Host 1,073 项和 Client 982 项安装文件的路径与哈希。
- Ubuntu 22.04 WSL2 启动了 x64 图形客户端，并用上一版 Linux Host 的正常命令从 GitHub 增量下载了 0.1.8。下载 166,489 字节，完整重建文件与已发布安装包逐字节相同。ARM64 包检查了 ELF 架构和更新程序的执行权限。
- macOS 三种包检查了应用版本、Mach-O 架构和执行权限。iOS IPA 通过 Xcode 的 iphoneos / arm64 构建及标识检查。
- 核心测试覆盖范围请求、完整返回、无旧包、缓存命中、截断、错位的 Range、索引损坏、内容损坏及防止版本回退。
